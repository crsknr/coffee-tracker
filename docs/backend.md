# Coffee Tracker - Backend API Documentation

---

## 1. Overview

Single Google Apps Script web app serving as the backend for the Coffee Tracker. All data is stored in a Google Sheet with 5 tabs. The API provides GET endpoints for reading data and a single POST endpoint for all write operations.

**Base URL:** `https://script.google.com/macros/s/<DEPLOYMENT_ID>/exec`

---

## 2. Sheet Structure

### 2.1 Transactions

Every action in the system is recorded as a row. This is the single source of truth, all other sheets are derived/cached.

| Column             | Type     | Description                                                                                          |
| ------------------ | -------- | ---------------------------------------------------------------------------------------------------- |
| Timestamp          | DateTime | When the transaction occurred                                                                        |
| User               | String   | Username                                                                                             |
| Type               | String   | `consume`, `purchase`, `settle`, `undo`                                                              |
| Item               | String   | Comma-separated item names (e.g. `Double,Oat Milk Portion`). For settle: `PayPal`. For undo: original items being reversed. |
| Quantity           | String   | Comma-separated quantities matching items (e.g. `1,2`). Negative for undo reversals (e.g. `-1,-2`).  |
| Amount (€)         | Number   | Net effect on user balance. Negative for consume, positive for purchase/settle, reversed for undo.   |
| Transaction ID     | String   | Unique ID generated by ESP32 (format: `esp32-<timestamp>-<hex>`)                                     |
| Ref Transaction ID | String   | Only for `undo` rows — references the Transaction ID being reversed. Empty for all other types.      |

**Example rows:**

```
2025-01-11 08:34:00 | Christoph | purchase | Beans,Cow Milk Carton,Oat Milk Carton | 5,8,6 | +75.30 | esp32-170490-a4f2 |
2025-01-10 16:34:00 | Christoph | consume  | Single                                | 1     | -0.30  | esp32-170491-b8e3 |
2025-01-10 11:01:00 | Christoph | consume  | Single,Oat Milk Portion               | 1,1   | -0.50  | esp32-170492-c2d5 |
2025-01-09 17:44:00 | Christoph | settle   | PayPal                                | 1     | +17.00 | esp32-170493-d1f6 |
2025-01-09 17:50:00 | Christoph | undo     | PayPal                                | -1    | -17.00 | esp32-170494-e2a7 | esp32-170493-d1f6
```

### 2.2 Users

| Column      | Type    | Description                                                |
| ----------- | ------- | ---------------------------------------------------------- |
| Name        | String  | Username (unique)                                          |
| Active      | Boolean | Whether user appears in the UI                             |
| Balance (€) | Number  | Current balance, incrementally updated on each transaction |

Balance is also derivable from `SUM(Amount)` across all Transactions for that user, but is cached here for fast lookups.

### 2.3 Inventory (Purchasables)

Current stock levels and thresholds.

| Column                | Type   | Description                                                                             |
| --------------------- | ------ | --------------------------------------------------------------------------------------- |
| Item Name             | String | Item name (e.g. `Beans`, `Cow Milk Carton`)                                             |
| Unit Size (kg/L)      | Number | Size of one unit in grams or milliliters                                                |
| Cost per Unit (€)     | Number | Purchase price per unit                                                                 |
| Critical Threshold    | Number | Units below this = red (needs immediate replenishment, displayed on screen)             |
| Low Threshold         | Number | Units below this = yellow (reminder to buy, triggers daily Telegram alert to treasurer) |
| Stock (units)     | Number | Sock in units (decimal, e.g. 1.94)                                             |

**Traffic light logic:**

- `dtock >= lowThreshold` → `green` (sufficient)
- `dtock >= criticalThreshold && stock < lowThreshold` → `yellow` (getting low, Telegram alert only)
- `stock < criticalThreshold` → `red` (critical, displayed on user page)

### 2.4 Products (Consumables)

Menu items with recipes and pricing.

| Column               | Type   | Description                                                                 |
| -------------------- | ------ | --------------------------------------------------------------------------- |
| Item Name            | String | Item name (e.g. `Single`, `Double`, `Cow Milk Portion`)                     |
| Recipe               | String | Ingredient formula (e.g. `Beans:0.016,Water:0.060`) — `InventoryItem:grams_or_ml` |
| Calculated Price (€) | Number | Raw cost based on recipe × inventory unit costs                             |
| Price (€)            | Number | Actual charge price (includes markup for waste/errors)                      |

### 2.5 Config

Key-value pairs for system configuration.

| Key                  | Example Value       | Description                                          |
| -------------------- | ------------------- | ---------------------------------------------------- |
| `treasurer`          | `Christoph`         | User who buys stock and receives payments            |
| `paypal_link`        | `paypal.me/crsknr`  | PayPal.me link for settlements                       |
| `balance_threshold`  | `-10.00`            | Balance below this triggers QR payment screen        |
| `telegram_bot_token` | `123456:ABC-DEF...` | Telegram bot token for notifications                 |
| `telegram_chat_id`   | `987654321`         | Telegram chat ID for notifications                   |
| `daily_report_hour`  | `8`                 | Hour (0-23) when the daily inventory report is sent  |

## 3. GET Endpoints

### 3.1 `GET ?action=getConfig`

**Request:**

```
GET <BASE_URL>?action=getConfig
```

**Response:**

```json
{
  "status": "success",
  "users": [
    {"name": "Christoph", "balance": -15.40, "isTreasurer": true},
    {"name": "Laura", "balance": -3.20, "isTreasurer": false},
    {"name": "Jonathan", "balance": 0.00, "isTreasurer": false}
  ],
  "products": [
    {"name": "Single", "price": "0.30€"},
    {"name": "Double", "price": "0.60€"},
    {"name": "Cow Milk Portion", "price": "0.20€"},
    {"name": "Oat Milk Portion", "price": "0.20€"}
  ],
  "inventory": [
    {"item": "Beans", "price":  "30€ / 1kg", "stock": "1.350kg", "status": "red"},
    {"item": "Water", "price":  "0.85€ / 2L", "stock": "4.670L", "status": "green"},
    {"item": "Cow Milk Carton", "price":  "1.69€ / 1L", "stock": "4.170L", "status": "yellow"},
    {"item": "Oat Milk Carton", "price":  "2.55€ / 1L", "stock": "6.670L", "status": "green"}
  ],
  "config": {
    "treasurer": "Christoph",
    "paypalLink": "paypal.me/crsknr",
    "balanceThreshold": -10.00,
    "criticalInventoryItem": "Low on Beans!"
  }
}
```

**Field details:**

- `users`: Active users sorted by name. `balance` is from the Users sheet. `isTreasurer` is `true` if the user matches the `treasurer` config value.
- `products`: Consumable items from Products sheet. `price` is the markup price (Price column, not Calculated Price).
- `inventory`: Purchasable items from Inventory sheet. `status` is the traffic light color based on thresholds.
- `config.criticalInventoryItem`: Display-ready string for the user page subtitle. `""` if no items are at critical level, otherwise `"Low on Beans!"` (the most critical red item). Yellow (low) items are not displayed, they only trigger Telegram alerts.

### 3.4 `GET ?action=getLastTransactions&user=<n>&limit=<n>`

Transaction history for the account_info page. Returns expanded rows (multi-item transactions split into individual display rows).

**Request:**

```
GET <BASE_URL>?action=getLastTransactions&user=Christoph&limit=10
```

**Response:**

```json
{
  "status": "success",
  "transactions": [
    {"timestamp": "11.01 | 08:34", "action": "Purchase", "item": "Beans", "qty": "5", "amount": "+75.30"},
    {"timestamp": "", "action": "", "item": "Cow Milk", "qty": "8", "amount": ""},
    {"timestamp": "", "action": "", "item": "Oat Milk", "qty": "6", "amount": ""},
    {"timestamp": "10.01 | 16:34", "action": "Consume", "item": "Single", "qty": "1", "amount": "-0.30"},
    {"timestamp": "10.01 | 13:43", "action": "Consume", "item": "Single", "qty": "1", "amount": "-0.30"},
    {"timestamp": "10.01 | 11:01", "action": "Consume", "item": "Single", "qty": "1", "amount": "-0.50"},
    {"timestamp": "", "action": "", "item": "Oat Milk", "qty": "1", "amount": ""},
    {"timestamp": "10.01 | 08:42", "action": "Consume", "item": "Single", "qty": "1", "amount": "-0.50"},
    {"timestamp": "", "action": "", "item": "Oat Milk", "qty": "1", "amount": ""},
    {"timestamp": "09.01 | 17:44", "action": "Settling", "item": "PayPal", "qty": "17.00", "amount": "+17.00"}
  ]
}
```

**Row grouping logic:**

Multi-item transactions are expanded into one row per item. Only the first row of each group gets `timestamp`, `action`, and `amount`. Subsequent rows in the same transaction have empty strings for those fields.

**Display mapping:**

Each array element maps directly to one display row on the Nextion:

- `timestamp` → `account_info.rowN_date.txt`
- `action` → `account_info.rowN_action.txt`
- `item` → `account_info.rowN_item.txt`
- `qty` → `account_info.rowN_qty.txt`

Empty strings after the `limit` are not returned, the ESP fills remaining row slots with empty strings.

**Action type formatting:**

| Transaction type | Display action |
| ---------------- | -------------- |
| `consume`        | `Consume`      |
| `purchase`       | `Purchase`     |
| `settle`         | `Settling`     |
| `undo`           | `Undo`         |

**Amount formatting:**

- Consume: `-0.30` (negative, money owed)
- Purchase: `+75.30` (positive, credit earned)
- Settle: `+17.00` (positive, debt cleared)
- Undo: reversed sign of original

## 4. POST Endpoint

All write operations use a single POST endpoint. The `type` field determines behavior.

**Request URL:** `POST <BASE_URL>`  

**Content-Type:** `application/json`

### 4.1 Consume

**Request:**

```json
{
  "user": "Christoph",
  "type": "consume",
  "items": ["Double", "Oat Milk Portion"],
  "quantities": [1, 2],
  "transactionId": "esp32-1704900000-a4f2"
}
```

**Backend actions:**

1. Check for duplicate `transactionId` → return `duplicate` if found
2. Look up `Price` for each item in Items sheet
3. Calculate total amount: `(1 × 0.60) + (2 × 0.20) = -1.00`
4. Parse recipes and deduct inventory (e.g. Double recipe `Beans:0.016,Water:0.060` → Beans -0.016 units, Water -0.06 units)
5. Write one row to Transactions: `consume | Double,Oat Milk Portion | 1,2 | -1.00`
6. Update Users sheet: `Balance += amount` (i.e. Balance -= 1.00)
7. Evaluate stock thresholds, determine `criticalInventotyItem`

**Response:**

```json
{
  "status": "success",
  "balance": -16.40,
  "criticalInventotyItem": "Low on Beans!"
}
```

---

### 4.2 Purchase

**Request:**

```json
{
  "user": "Christoph",
  "type": "purchase",
  "items": ["Beans", "Oat Milk Carton"],
  "quantities": [2, 6],
  "transactionId": "esp32-1704900003-c5d6"
}
```

**Backend actions:**

1. Check for duplicate `transactionId`
2. Look up `Cost per Unit` for each item in Inventory sheet
3. Calculate total amount: `(2 × 30.00) + (6 × 2.55) = +75.30`
4. Add to inventory: Beans +2 units, Oat Milk Carton +6 units
5. Write one row to Transactions: `purchase | Beans,Oat Milk Carton | 2,6 | +75.30`
6. Update Users sheet: `Balance += 75.30`
7. Evaluate stock thresholds

**Response:**

```json
{
  "status": "success",
  "balance": 59.90,
  "criticalInventotyItem": ""
}
```

---

### 4.3 Settle

**Request:**

```json
{
  "user": "Bob",
  "type": "settle",
  "amount": 17.00,
  "transactionId": "esp32-1704900005-f1a2"
}
```

The `amount` is the absolute balance value as displayed on the ESP when the user scanned the QR code. Always the full outstanding balance.

**Backend actions:**

1. Check for duplicate `transactionId`
2. Write one row to Transactions: `settle | PayPal | 1 | +17.00`
3. Update Users sheet: `Balance += 17.00`
4. No inventory changes
5. Send Telegram notification: `"💰 Bob settled €17.00 — check PayPal"`

**Response:**

```json
{
  "status": "success",
  "balance": 0.00,
  "criticalInventotyItem": ""
}
```

---

### 4.4 Undo

Reverses the user's most recent non-undo transaction.

**Request:**

```json
{
  "user": "Christoph",
  "type": "undo",
  "transactionId": "esp32-1704900006-b3c4"
}
```

No items, quantities, or amount needed, the backend determines everything from the transaction being reversed.

**Backend actions:**

1. Check for duplicate `transactionId`
2. Find the most recent non-undo transaction for this user
3. If not found or most recent is already an undo → return error
4. Write one row mirroring the original with reversed values:
   - Same items, negated quantities, reversed amount
   - `Ref Transaction ID` = original's Transaction ID
5. Reverse inventory changes (if the original was consume or purchase)
6. Update Users sheet: `Balance += reversedAmount`
7. Evaluate inventory thresholds
8. If the undone transaction was a `settle`: send Telegram notification `"↩️ Bob undid settlement of €17.00"`

**Example undo row for a consume of "Double,Oat Milk Portion | 1,2 | -1.00":**

```
Christoph | undo | Double,Oat Milk Portion | -1,-2 | +1.00 | esp32-yyy | esp32-xxx
```

**Response:**

```json
{
  "status": "success",
  "balance": -15.40,
  "criticalInventotyItem": "Low on Beans!"
}
```

## 5. Error Handling

### 5.1 Error Response Format

```json
{
  "status": "error",
  "error": "<error message>"
}
```

### 5.2 Error Types

| Error                                  | When                                     |
| -------------------------------------- | ---------------------------------------- |
| `Missing field: <field>`               | Required field not in request            |
| `Unknown user: <n>`                    | User not found or not active             |
| `Unknown item: <n>`                    | Item not in Products or Inventory sheet  |
| `Nothing to undo`                      | No transactions found for user           |
| `Last transaction is already an undo`  | Prevents undo chains                     |
| `Items and quantities length mismatch` | Arrays don't match                       |

### 5.3 Duplicate Handling

If a `transactionId` already exists in the Transactions sheet, the backend returns:

```json
{
  "status": "duplicate",
  "balance": -15.40,
  "criticalInventotyItem": ""
}
```

No data is modified. The current balance is returned so the ESP can proceed normally. This makes the API idempotent and safe for retry/sync scenarios.

## 6. Notifications

### 6.1 Telegram Integration

The backend sends notifications via a Telegram bot. Configuration is stored in the Config sheet (`telegram_bot_token`, `telegram_chat_id`). If either value is missing or empty, notifications are silently skipped.

### 6.2 Settlement Alerts (Immediate)

Sent synchronously as part of the POST response for `settle` and `undo` of `settle` transactions. Adds ~500ms-1s to the response time.

| Trigger                | Message                                |
| ---------------------- | -------------------------------------- |
| User settles balance   | `💰 Bob settled €17.00 — check PayPal` |
| User undoes settlement | `↩️ Bob undid settlement of €17.00`   |

### 6.3 Daily Inventory Report (Scheduled)

A time-based Apps Script trigger runs once daily (configured via `daily_report_hour` in Config, default 8am). It checks all inventory levels against both thresholds.

**If any items are below low or critical threshold:**

```text
☕ Daily Inventory Report

🔴 Beans: 450g (critical — below 500g)
⚠️ Oat Milk: 2100ml (low — below 3000ml)

Everything else OK.
```

**If all items are above thresholds:** no message is sent.

The trigger is installed by running `createDailyTrigger()` once during initial setup.

## 7. Transaction ID Format

Generated by the ESP32 at the time the transaction occurs (not at sync time).

**Format:** `esp32-<millis>-<random_hex>`

**Example:** `esp32-1704900000-a4f2`

```cpp
String generateTransactionID() {
  unsigned long timestamp = millis();
  uint16_t random_val = random(0, 65535);
  return "esp32-" + String(timestamp) + "-" + String(random_val, HEX);
}
```

## 8. Implementation Notes

### 8.1 Inventory Deduction (Consume)

When processing a consume transaction, the backend:

1. Looks up each item in the Items sheet to get the Recipe
2. Parses the recipe (e.g. `Beans:0.016,Water:0.060` means 0.016kg beans + 0.060L water)
3. Deducts from Inventory sheet's `Current Stock`

### 8.2 Inventory Addition (Purchase)

When processing a purchase transaction:

1. The items are Inventory items directly (e.g. `Beans`, `Cow Milk Carton`)
2. Quantities are in whole units (e.g. 2 bags of beans)
3. Adds to Inventory sheet's `Current Stock`
4. Cost is `quantity × Cost per Unit` from Inventory sheet

### 8.3 Critical Inventory Item Determination

After every write transaction, the backend evaluates all inventory items against the **critical threshold** only (not the low threshold — that's for Telegram alerts only):

1. Find all items with `red` status (`stock < criticalThreshold`)
2. If any red items exist: return the one with the lowest stock relative to its threshold (most critical)
3. Format as display-ready string: `"Low on Beans!"`
4. If no red items: return `""`

### 8.4 Balance Updates

The Users sheet `Balance` column is updated incrementally on every transaction. The amount from the Transactions row is simply added to the current balance:

`Balance = Balance + amount`

Since `amount` is already signed correctly (negative for consume, positive for purchase/settle, reversed for undo), this single operation handles all cases.

### 8.5 Timestamp Formatting

For `getLastTransactions`, timestamps are formatted as `DD.MM | HH:MM` in the backend. The ESP pipes these strings directly to the Nextion display.

### 8.6 Amount Formatting

For `getLastTransactions`, amounts are formatted with sign prefix: `-0.30` (consume), `+75.30` (purchase/settle).

For POST responses, `balance` is a raw number (e.g. `-16.40`). The ESP formats it for display (e.g. `"-16.40€"`).
